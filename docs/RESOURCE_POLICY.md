# 当前资源政策：单次求解超时，累计核时不限

更新：2026-10-24（美东）。最新用户指令：“那还是应该加一个合理的超时限制”。采用每题每方法 **3600 CPU秒** 的统一求解上限；项目与阶段累计核时仍不限。本文优先于旧目标中“正式求解无限运行”的要求。

## 执行规则

- 新实验每个基础实例的每种固定模式，完整进程树CPU上限3600秒。
- 在线策略的观察、解析、选择、重启和正式求解合计最多3600秒；不是probe后再给正式臂3600秒。独立答案检查另行记账；检查未通过不得算已解。
- 观察窗口仍是算法参数，不改变总上限；oracle取证可以有更短的显式界，但必须单独标注。
- 当前正在运行的旧55题和外推作业，在执行端同步政策后检查累计CPU：尚未求解且已达3600秒的，保存日志与必要证明后停止，记为policy_timeout。已求解正在独立验证的任务继续验证。
- 历史运行、冻结协议、已有完整结果不覆盖。超过新截止才完成的历史结果可用于无截止历史分析；新截止比较必须标为超时。无法从历史轨迹确定在线策略在截止前状态时，标不可重建，不编造截断结果。
- 不为了跑完超时题自动放宽上限、反复重启或换seed。特别长的个案研究以后另设清单和协议，不阻塞主研究。
- 保留失败、终止及历史重跑的真实CPU账本，不把运行至今的数小时成本改写为3600秒。

## 评价规则

完整平均时间的定义保持不变：同一预先固定面板的某方法全部完成并验证后才报告；有超时则其完整均值为null。不能用3600秒代替完成时间，也不能只平均各自解出的题。

对有超时面板，先报告统一3600秒内的已解数、SAT/UNSAT分层、解题随CPU时间变化的曲线及超时清单。共同完成子集的配对均值仅作次要描述，标出筛选偏差。暂不自动启用PAR2或其他惩罚均值作为主指标；需要标量排序时另行明确协议。新生成主面板优先利用独立pilot选择可在截止内覆盖的规模，但冻结后不删除超时题或按策略赢家挑题。

已完成的v9 270题比较保持原有冻结协议与数字，不追溯改成另一项预注册实验。若另提供3600秒视图，明确它是事后敏感性分析。

## 接入状态与执行目标

本次提交更新政策和下一执行目标，**不代表远端正在运行的进程已被停止**。旧 configs/resource_policy.json 与 scripts/resource_policy.py 是先前无限单次运行政策的实现，不能直接当作新超时已生效。新配置为 [run_timeout_policy.json](../configs/run_timeout_policy.json)。

执行agent下一步必须先：
1. 盘点远端作业及验证状态，安全停止达到截止且未求解的作业，提交实际停止时间与逐题清单。
2. 接入v7/v8/v9实际控制器及wrapper；保留累计核时不限，统一进程树CPU计时，新增policy_timeout状态和新政策run_id，避免旧结果被跳过或覆盖。
3. 用可控子进程验证固定臂、probe后重启的总计时、已出答案的独立验证以及历史记录兼容，再发布运行配置。
4. 重建旧55题与外推进度报告，分别呈现旧无限运行结果与新3600秒评价；只对有充足轨迹的历史记录重建。
5. 后续研究以秒级到分钟级的多规模面板为主，极难比赛题在统一截止下作压力测试。

旧无累计核时限制授权继续有效。累计200核时及任何阶段核时额度均不得恢复。
