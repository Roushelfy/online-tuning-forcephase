# v7 长时运行计划（C0：在任何 v7 求解运行之前提交）

日期：2026-10-23（UTC 约 22:50）。本文具体化 [Agent Goal v7](AGENT_GOAL.md) 与 [COMPLETION_TIME_PROTOCOL_V7.md](COMPLETION_TIME_PROTOCOL_V7.md) 的执行方式。机器可读版本：[configs/completion_v7/run_plan.json](../configs/completion_v7/run_plan.json)。

**提交前没有做**：任何 v7 求解运行。

**账本**：v6 之后累计 144.65 CPU 核时；用 `sacct` 核对，v6 之后本项目没有新的作业。累计上限 200，**可用 55.35**。

## 1. 复用审计（`scripts/completion_v7/reuse_audit.py`）

**固定动作 D、F+、F−**（v6 的 `v6_validate_fixed`）：
- 适用条件：二进制（`build/fpc`，sha256 6cf08469…）、命令参数、seed 0、LRAT 证明与遥测政策，都与 v7 完全相同。
- 已解出且独立验证通过的记录，复用为 `solved`，CPU 取原记录的进程 CPU（wait4），**不取 cost 列**。
- 在 300 s 被终止的记录，复用为 `censored`，CPU 取实际执行的进程 CPU（≥ 300 s），只作下界。

**P1_M05_long**：
- 定义：冻结的 v6 `P1_M05_final`，选动作逻辑与模型完全不变，只去掉正式求解的“剩余 300 s 预算”停止条件。
- v6 wrapper 已解出且验证通过的记录：它的正式求解没有碰到 300 s 限制，轨迹与长时版逐项相同，复用为 `solved`，CPU 取完整进程树的 wait4 CPU。
- v6 wrapper 在 300 s 被终止的记录：作为 `censored` 下界。

**审计输出**：每条复用都保留原 run_id 与参数比对结果，存于 `results/completion_v7/reuse_audit.csv`。

## 2. 长时运行入口

**P1_M05_long**（`scripts/completion_v7/wrapper_long.py`）：
- 观察部分与 v6 wrapper 相同：obsprofile6 计算 S28，静态上限 3 s，没做完就选 D；冻结的读出器给出动作。
- 选定动作后，用 `exec` 把自身进程替换为正式求解器，命令与 v6 及固定运行一致：`build/fpc/cadical --lrat=1 <动作参数> --fpc=1 <cnf> <proof>`，内存上限 16 GB。
- 正式求解没有评分截止。
- 整个进程（含观察子进程）的 CPU 由运行器通过 wait4 计时；exec 之前的 CPU 记为 `cpu_at_exec`。

**固定动作**：运行器直接启动同样的求解器命令。

**运行器**（`scripts/completion_v7/longrun.py`）：
- 每个运行绑定一个物理核。
- 证明写在节点本地磁盘 `/var/tmp`（5.2 TB），不写到内存盘或共享盘。
- 解出后立即做独立检查：SAT 用 checkmodel；UNSAT 用 lrat-trim，时限 max(1800 s, 4 × 求解 CPU)，内存 64 GB。检查完删除证明，只保留大小。
- 每 60 s 把每个运行的实际 CPU 写成心跳。
- 行政停止：先 SIGTERM，CaDiCaL 会正常退出，60 s 后才 SIGKILL。停止时记 `censored`，CPU 取 wait4 的实际 CPU。
- 错误、OOM 和未验证的答案都记 `error`，不作下界。

## 3. D 的测量来自同一次搜索（预先固定）

在 v6 wrapper 未解出的 28 题上，P1_M05_long 的观察结果都是选 D 或回退 D。它的正式求解就是一次**从头开始、单独进程**的完整 D 运行：二进制、参数、seed、输入与证明政策都与固定 D 相同，搜索是确定性的。

因此在这些题上：
- **D 的测量**取这次正式求解的求解器 CPU，即 wait4 总 CPU − `cpu_at_exec`。来源是该 wrapper 运行，标记为 `formal subprocess`。
- **P1_M05_long 的测量**取完整进程树 CPU。

这样避免同一个确定性搜索跑两遍，也使“P1_M05_long − D”在这些题上恰好等于观察与 wrapper 开销。若 wrapper 在某题选了非 D 动作，该题的 D 另行单独运行。

**每个“实例 × 方法”的采用顺序**（只取第一条满足的，不挑最快）：
- **D / F+ / F−**：
  1. v6 固定运行的已验证解出；
  2. v7 的单独长时运行（解出或删失）；
  3. 仅对 D：v7 P1_M05_long 中选 D 的正式求解；
  4. v6 固定运行的 300 s 删失下界。
- **P1_M05_long**：
  1. v6 wrapper 的已验证解出；
  2. v7 长时 wrapper；
  3. v6 wrapper 的删失下界。

## 4. 调度与预算

**阶段 1：补齐 D 基线与 P1_M05_long，求解与 wrapper CPU 上限 40 核时**
- 运行内容：
  - 28 题 P1_M05_long 长时 wrapper（D 的测量同时取自其中，见第 3 节）；
  - 1 题单独的长时 D：`761651d4b6`，P1 在该题选 F+，v6 中已解出。
- 公平调度：29 个运行同时启动，每个占一个核，所以未完成的运行始终得到相同的 CPU。
- 停止条件：所有运行累计 CPU（已结束的加上正在运行的）达到 40 核时，统一行政停止。
- 运行放在 1 个独占节点上：48 个物理核、1.5 TB 内存、5.2 TB 本地盘。

**阶段 2：为 oracle 取证，上限 10 核时，只在阶段 1 结束后进行**
- 适用的题：v6 中三个动作都没在 300 s 内解出、而阶段 1 中 D 在 b > 300 s 时解出的题。
- 运行内容：F+、F− 从头运行，直到解出，或实际 CPU 达到 b 后停止，记为 `noncompetitive_bound`。
- 优先级与停止：先跑 b 最小的题，题与题之间不挑；达到 10 核时即停止。

**其余题的 oracle**：
- v6 中至少一个动作已在 300 s 内解出、且其余动作的 300 s 下界 ≥ 该时间的题，oracle 已经由复用记录确定。
- 阶段 1 仍未解出 D 的题，oracle 保持未定。

**预留**：≥ 5.35 核时，用于检查器、分析、必要的重跑和报告。检查器 CPU 计入研究账本，不计入主指标。

**中断**：若 Slurm 作业被中断，最后一次心跳的实际 CPU 作为 `censored` 下界，并单独标注；不把两次从头运行拼接成一次。

## 6. 偏离记录

1. **阶段 1 不是独占节点**（提交后、任何 v7 求解之前）：
   - 原因：cpu-low 的每个节点都有一半核被其他分区的作业占用，没有可独占的节点，独占作业无法调度。
   - 改为：非独占地申请 72 个逻辑 CPU，即 36 个物理核；每个运行仍绑定一个独立的物理核，内存 700 GB。
   - 影响：主指标是 CPU 时间，但同节点其他作业的内存带宽竞争可能使 CPU 时间略增。这种影响同时作用于共用同一次运行的 D 与 P1_M05_long，所以不影响两者在共用题上的差值。报告会单独标出阶段 1 的计时条件与 v6 复用记录不同，后者来自独占节点。
2. **第一次提交跑错了硬件**（作废，没有使用任何结果）：
   - 原因：第一次非独占提交（作业 744153）没有用数组作业形式，sbatch 里的 gs-srun 因此在默认的 hpc-mid 分区另起了作业 744154，运行在 H100 节点 h100-206-173 上。它的 CPU 与 v6 记录不同，计时不可比。
   - 处理：约 2 分钟后发现并取消，没有任何完成记录，只有一个心跳文件，留档于 `runs/completion_v7/void_stage1_h100_744154`。
   - 计费：作废尝试按 29 核 × 130 s 的上限 1.05 CPU 核时记账，见 `results/completion_v7/voided_attempts.json`。
   - 重新提交：以 `--array=0-0` 提交，仍为 72 个 CPU 的非独占分配，重新从头运行。
3. **阶段 1 的进程内心跳只写了一次**（运行中发现，不影响任何结果记录）：
   - 原因：`longrun.py` 用 `fprun.atomic_write_json` 写 `progress.json`，这个函数为保护结果记录而“从不覆盖已有文件”，所以第一次之后的心跳都被静默丢弃。每个运行的结果记录只写一次，不受影响。
   - 处理：没有重启正在运行的阶段 1。`longrun.py` 改为心跳用覆盖写（`replace_json`），只影响以后的阶段；阶段 1 另用 `scripts/completion_v7/external_heartbeat.py` 从作业节点的 `/proc` 定期采样每个进程的实际 CPU，写入 `runs/completion_v7/stage1/heartbeat_external/`（只新增不覆盖）。
   - 影响：心跳只用于控制器崩溃时给出实际下界；正常结束时以每个运行的结果记录为准。
4. **阶段 2 的预算按实际账本确定**（阶段 1 结束前写定，此时还没有看到任何阶段 1 删失结果）：
   - 原因：作废尝试的 1.05 核时与阶段 1 停止时的少量超出都已用掉部分预留。
   - 规则：阶段 2 预算 B2 = min(10, 200 − 已记账 − 2.0) 核时。“已记账”包括 v7 之前的 144.65、作废尝试、阶段 1 的求解/wrapper CPU、阶段 1 的检查器 CPU，以及 1.0 核时的分析估计；2.0 核时留给阶段 2 的检查器与最终报告。
   - 阶段 2 的入选题与优先级不变（第 4 节：b 最小者先跑）。规划器保证各臂上限之和 ≤ B2，运行器的预算停止作为第二道保护。
