# v10 S0：旧实验审计（v4–v9）

日期：2026-10-26（UTC）。目标：[Agent Goal v10](../../docs/AGENT_GOAL.md)。本文与协议 [CROSS_SCALE_PROTOCOL_V10.md](../../docs/CROSS_SCALE_PROTOCOL_V10.md) 一起，在任何 v10 新求解之前提交。

本文回答两件事：

1. 本轮的三个观察族（静态 A、默认前缀 B、三模式配对前缀 C）在项目中各自试过什么、结果如何、这次改了什么。原则是不把旧的负结果换个名字重跑。
2. 3600 s 进程树计时、超时与检查失败状态、run_id 隔离、证明处理和日志时序，在 v10 开始前是否可靠。

**结论**：A、B、C 三族在项目中都有前身。本轮可能新增的价值只能来自四方面：

- 跨规模设计：开发三档、外推一档；
- 以开发 SBS 为基线的保守门；
- 与同成本无内容对照的直接比较，用来分清“多试几种模式”和“读出内容”的贡献；
- 冻结后的真实部署。

如果 C 在计入开销后不胜过 N_C，结论就是“只有预求解或调度收益”。

## 2. 基础设施审计（3600 s 政策之后）

| 项目 | 现状与证据 | v10 处理 |
|---|---|---|
| **3600 s 进程树计时** | 控制器在 cap 处 SIGTERM，60 s 后 SIGKILL；固定运行另设内核 RLIMIT_CPU。wrapper 的 probe 都是被等待的子进程，正式求解 exec 在同一进程，exec 前按剩余预算设 RLIMIT_CPU（`scripts/run_timeout_policy.py`，[RUN_TIMEOUT_APPLICATION.md](../../docs/RUN_TIMEOUT_APPLICATION.md)） | v10 wrapper 有新的计时语义：静态分析 + 最多三个 probe + 重启，所以补了受控子进程测试 `tests/test_cross_scale_v10.py`：伪求解器下静态分析、三个 0.3 s probe 与重启合计受同一个 1.5 s 上限；第一个 probe 的答案经真实 checkmodel 验证后直接返回，后续 probe 不再运行；MEASURE 模式中每个 probe 独立运行。3 项测试通过；已有 26 项超时测试不重复 |
| **超时与检查失败状态** | `policy_timeout`：到达上限，或越过上限才给出答案；lrat-trim 内存不足记为 `unverified`，不算已解；`censored` / `platform_disk` 是平台中断；`error` 是其他失败 | 沿用。报告中把超时、平台中断、未验证、错误与不可重建分开列 |
| **run_id 隔离** | id = sha1（phase、stage、实例、CNF 哈希、方法、seed、求解器哈希、cap、run_policy_id …） | phase 改为 `cross_scale_v10`，不会与 v9 记录冲突；W 与 MEASURE 的 id 另含 wrapper、common、twlib、static10 与策略文件的 sha256，所以冻结后的任何代码改动都会产生新 id，旧记录不会被跳过或覆盖 |
| **证明处理** | 证明写在节点本地 `/var/tmp`，检查后删除；本地盘低于 300 GB 时停止证明最大的运行，记为 `platform_disk` | 沿用（`/var/tmp/fp_v10_<user>`）。probe 未解时证明立即删除；MEASURE 不保留证明，也不检查答案（只记录退出码，与固定运行的已验证答案核对） |
| **日志时序** | 每条记录有 start / end UTC、主机、Slurm 作业号；progress.json 每 60 s 心跳；v9 外推作业曾被 Slurm 自动重新排队，2 个运行被杀且无记录 | v10 的 sbatch 加 `--no-requeue`：节点故障时作业失败而不是静默重跑，补跑用新 stage 并保留历史 |
| **共享数据盘** | 2026-10-26 `/mnt/data` 已用 795 / 800 TB（剩余 5.2 TB），2026-10-23 曾写满 | v10 的记录与 CNF 只有 GB 级；每个阶段开始前检查剩余空间。一旦写满，按平台中断记录并在新 stage 补跑 |
